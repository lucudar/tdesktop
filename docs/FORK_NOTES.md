## Схема работы

1. Пользователь присылает идею → агент вносит правку в отдельной ветке и открывает PR в `dev`.
2. Сборка идёт в отдельном публичном репозитории **`lucudar/telewhite-build`** (в
   `lucudar/tdesktop` GitHub отключил Actions, см. «Перенос в `lucudar/tdesktop`»).
   Его workflow `.github/workflows/build.yml` — копия `win.yml` (Release): скачивает код из
   `lucudar/tdesktop` и собирает `Telegram.exe`. Что собрать — первая строка `build-ref.txt`
   (ветка, тег или коммит), коммит этого файла запускает сборку; вручную — Run workflow с
   полем `ref`. Артефакт — `Telewhite x64 <10 знаков коммита>`, хранится 7 дней.
   Сборка — Ninja с кэшем папки `out`: пересобирается только изменённое (см. «Ускорение CI»).
3. Пользователь скачивает артефакт со страницы Actions репозитория `telewhite-build`,
   тестирует на своём ПК (Windows) и вливает PR в `dev`.
4. Если предыдущий PR ещё не влит, следующий открывается поверх его ветки (база PR —
   ветка предыдущего). После мерджа первого второй перенацеливается на `dev`
   (GitHub делает это сам, когда ветку первого удаляют).

## Что уже настроено

- CI урезан до одной сборки **Windows x64** (была матрица из 6 вариантов).
- Удалены workflows: linux, mac, mac_packaged, snap, docker.
- Удалены и апстримовские workflows-обслуживание: canary, issue-боты, winget, stale
  (форку-приложению они не нужны, только шум в CI). Остался только `win.yml`:
  `changelog.yml` удалён 20.10.2026 — он публикует GitHub Pages, которых у форка нет,
  и падал на каждом мердже апстрима.
- В `win.yml` добавлен `workflow_dispatch` (ручной запуск сборки).
- Все сборки идут на бесплатных `windows-latest`: апстрим собирает PR, теги и `nightly`
  на платных раннерах `depot-windows-latest-16`, в форке такие задачи висели бы в очереди
  вечно. PR из веток этого же репозитория отдельно не собираются — их проверяет
  push-прогон ветки (тот же коммит); PR из чужих форков собираются как обычно.
- API-ключи: если в Secrets репозитория заданы `TDESKTOP_API_ID` и `TDESKTOP_API_HASH`,
  сборка использует их, иначе — тестовые ключи (`-D TDESKTOP_API_TEST=ON`).
- Артефакт хранится 7 дней (у апстрима 1 день — не успевали скачать).
- С 21.10.2026 сборка **Release**: библиотеки собираются в обеих конфигурациях
  (`win.bat silent`), кэши под ключами `libs-release-` и `qt-release-`, приложение —
  `--config Release`, артефакт из `out\Release`. Холодная сборка новой ветки в zet1 шла
  3–3,5 часа, а в 3213123 — 5 ч 38 мин и 5 ч 54 мин, почти до лимита GitHub в 6 часов на
  задачу. Кэши библиотек сохраняются до сборки приложения: если холодная сборка упрётся в
  лимит, перезапуск пойдёт уже с кэшем. Кэши GitHub видны только своей ветке и `dev`.
  Release-стадия breakpad собирает `dump_syms`, которому нужен ATL для закреплённого
  тулсета 14.44, а на раннере ATL есть только для новейшего: шаг «ATL for the 14.44
  toolset.» ставит `Microsoft.VisualStudio.Component.VC.14.44.17.14.ATL` при промахе кэша.
- Места на диске впритык. На образе Windows Server 2025 нет отдельного D:, всё лежит на C:
  (около 150 ГБ, свободно около 30). Шаг «Free disk space on C.» удаляет неиспользуемый
  предустановленный софт: Android, .NET SDK, LLVM, `C:\msys64`, Strawberry Perl, системный
  Rust, лишние версии Python, базы данных и т. п. `prepare.py` ставит свои msys64, perl и Rust.
  После мерджа 7.3.2 (+ ANGLE для Qt 6) старой очистки не хватило: библиотеки упали на
  `tg_owt` с «No space left on device». Свободное место печатается в начале и в конце шага
  очистки и в шаге «Disk space after libraries.».
- Апстрим синхронизирован до **7.4.0** (слияние 05.11.2026, батч 19, тег `v7.4.0`;
  до этого — 7.3.2, мердж 21.10.2026, батч 10). Как сливать — «Как обновлять апстрим».

## Как обновлять апстрим

```bash
git fetch --depth=3200 upstream dev
git merge upstream/dev
```

Если у агента нет `git push` (только GitHub API), слияние делает сам GitHub (батч 19):
1. Локально слить апстрим и решить конфликты, чтобы знать итоговые файлы.
2. В ветке форка коммитом через API взять конфликтующие файлы в версии апстрима и вернуть
   удалённые в форке workflow апстрима с условием
   `if: github.repository == 'telegramdesktop/tdesktop'` — тогда конфликтов нет.
3. Открыть PR в эту ветку из `telegramdesktop:dev` (на момент релиза `dev` = тег) и влить
   его merge-коммитом.
4. Следующим коммитом вернуть версии Telewhite конфликтных файлов и прочие правки после
   слияния; проверить, что дерево ветки совпадает с локальным результатом.

Конфликты ожидаемы только в `.github/workflows/*` (форк держит свою схему CI)
и в `Telegram/SourceFiles/window/main_window.cpp` (строка заголовка окна:
сохранять `u"Telewhite"_q`, у нового кода есть ещё `+ suffix`).

## Полезные факты

- Ветка по умолчанию: `dev`. Пуши в неё триггерят сборку (кроме изменений `**.md` и `docs/**`).
- Артефакт называется `Telegram x64`, содержит `Telegram.exe` (Release-конфигурация).
- Первая сборка ~1.5–3 часа (собираются все библиотеки), дальше быстрее за счёт actions/cache.
- Логи прогонов `telewhite-build` без входа недоступны, аннотации — доступны (см.
  «Ускорение CI»): ошибки сборки читать через check-runs annotations.
- Лицензия GPLv3: исходники форка открыты; нельзя использовать имя «Telegram» и оригинальную иконку как есть.
- Для правок интерфейса смотреть `.style`-файлы и `Telegram/Resources/`;
  идеи фич можно подсматривать в форках 64Gram, Kotatogram, AyuGram, Forkgram.
- Пути в этом репозитории отличаются от апстрима: `.style`-файлы лежат в
  `Telegram/SourceFiles/<area>/*.style` (не в `Telegram/Resources/style/`),
  палитра — `Telegram/lib_ui/ui/colors.palette`, настройки чата —
  `Telegram/SourceFiles/settings/sections/settings_chat.cpp`.
  `Telegram/Resources/langs/lang.strings` — в репозитории LF (на Windows git может
  отдать CRLF), без BOM; вставлять байтово, не меняя окончания строк.
- Перед правками `git submodule update --init --depth=1` (иначе нет `.style` и палитры).
- Без Windows-сборки правки можно проверить на Linux: собрать `codegen_style`, `codegen_lang`
  и `codegen_emoji` из `Telegram/codegen`, сгенерировать стили, палитру, `lang_auto` и
  `scheme`, затем `g++ -std=c++20 -fsyntax-only` по изменённым `.cpp` с заголовками Qt 6.5
  и `-include stdafx.h`. CI собирает MSVC `/W4` с warnings-as-errors: неиспользуемые
  локальные переменные и функции ломают сборку. `-fsyntax-only` не ловит неиспользуемые
  функции — новые файлы проверять `-c -o /dev/null -Wall -Wextra`.
- На Windows Qt статическая (6.11), а локальная проверка идёт с динамической Qt 6.5, и
  одну ошибку компоновки так не поймать: функции, помеченные в заголовках Qt
  `QT_<МОДУЛЬ>_INLINE_SINCE(6, x)`, в статической сборке не inline (`modulecppexports.h.in`:
  «static builds treat everything as part of the library, so they never inline»). Их вызов
  подтягивает `removed_api.cpp.obj` модуля со всеми его зависимостями. Так
  `QNetworkRequest::setTransferTimeout(int)` (и такая же у `QNetworkAccessManager`) тянет
  `QDnsLookup` и требует `dnsapi.lib`, которого в списке библиотек нет (батч 18). Брать
  перегрузки с `std::chrono` (для Qt 6.5 — под `#if QT_VERSION >= QT_VERSION_CHECK(6, 7, 0)`)
  и перед новым вызовом сетевого API Qt проверять заголовок 6.11 на `INLINE_SINCE`.
- Стиль кода: табы, без комментариев-комментариев очевидного, `auto` для типов,
  строки через `u"..."_q`, новые настройки — через `writePref/readPref` (не QDataStream!).
- Требования к коммитам и стилю — в `AGENTS.md` и `REVIEW.md` в корне репозитория.

## Ускорение CI

Применено 04.11.2026 (коммит `e5a031cc23` в `lucudar/telewhite-build`, первый прогон
41850726014 — холодный, собирает батч 17). До этого каждая сборка компилировала приложение
с нуля: 137 из ~150 минут прогона 41795426329 — шаг «Telegram Desktop build.», библиотеки
уже брались из кэша.

- **Ninja вместо MSBuild** (`generator: ["Ninja Multi-Config"]`, как в матрице апстрима;
  имя артефакта прежнее — `Telewhite x64 <коммит>`). С Visual Studio генератором каждый
  файл, который подключает `lang/lang_keys.h` (~740 из ~1800 `.cpp`), видит все ключи из
  `lang_auto_keys.h`, и любая новая строка пересобирает их все. С Ninja апстримный
  `generate_lang.cmake` включает подмножества ключей: у каждого `.cpp` свой
  `lang_subsets/<путь>.cpp.h` (define `LANG_KEYS_SUBSET`), номера ключей стабильны
  (`lang_auto.indices`), а неизменённые файлы `codegen_lang` не перезаписывает. Новая строка
  пересобирает только файлы, где она используется. Проверка на Linux: `codegen_lang
  --subsets-only -o<gen> -s<SourceFiles> lang.strings` и компиляция с
  `-DLANG_KEYS_SUBSET="lang_subsets/<путь>.cpp.h"` (все файлы Telewhite проходят).
- **Кэш сборки** — папка `out` целиком (`actions/cache/restore` и `actions/cache/save`,
  ключ `Windows-x64-build-ninja-<CACHE_KEY>-<run_id>-<attempt>`, восстанавливается
  последний по префиксу). После checkout у всех файлов свежее время, поэтому шаг «Source
  timestamps for the build cache.» ставит дату 2020-01-01 файлам, чей blob не изменился с
  прошлой сборки (список `out/telewhite-sources.txt`: `git ls-files -s
  --recurse-submodules`), а изменённые и новые оставляет свежими — Ninja пересобирает только
  их и то, что от них зависит.
- Кэш сохраняется после успешной сборки, а также после неудачной, если кэш не
  восстанавливался (тогда все объектные файлы собраны из этих исходников). После неудачной
  сборки с восстановленным кэшем он не сохраняется: в `out` могли остаться устаревшие
  объектные файлы. Сборка идёт с `-k 0`, чтобы за один прогон собрать всё, что
  собирается, и увидеть все ошибки.
- Лимит кэшей репозитория — 10 ГБ, при превышении GitHub удаляет давно не использованные
  записи, а это могут быть кэши библиотек (их пересборка — 3–5 часов). Поэтому прошлая
  запись кэша сборки удаляется до сохранения новой (`gh cache delete`, нужен
  `permissions: actions: write`), а папка больше 30 ГБ не сохраняется (до батча 18 — 20 ГБ;
  после батча 17 папка весила 19 ГБ, а запись кэша — 1,6 ГБ). Размер папки —
  в аннотации «Build cache» прогона; размеры записей —
  `GET /repos/lucudar/telewhite-build/actions/caches` (без входа).
- **Ошибки без входа**: логи прогонов отдаются только с правами админа (403 без токена), а
  аннотации — всем: `GET /repos/lucudar/telewhite-build/check-runs/<id задачи>/annotations`
  (id задачи — из `/actions/runs/<id>/jobs`). Шаг «Problem matcher.» превращает ошибки
